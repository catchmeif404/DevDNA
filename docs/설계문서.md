# DevDNA 설계 문서

> GitHub 공개 활동 데이터를 분석해 개발자의 코딩 패턴, 기술 스택, 활동 시간, 개발 성향을 재미있게 보여주는 오픈소스 프로젝트

- 문서 버전: v0.1
- 상태: MVP 설계
- 목표: GitHub 로그인 → 데이터 수집 → 분석 → 개발자 유형/카드 생성 → 공유
- 라이선스 방향: MIT 검토

---

## 1. 프로젝트 개요

### 1.1 문제 정의

GitHub에는 개발자의 장기간 활동 데이터가 쌓이지만, 대부분의 개발자는 자신의 개발 습관과 프로젝트 활동을 재미있게 분석해볼 방법이 없다.

DevDNA는 GitHub 공개 활동 데이터를 기반으로 다음과 같은 정보를 제공한다.

- 총 Commit / PR / Repository 수
- 주요 프로그래밍 언어
- 가장 활발한 시간대
- 요일별 활동 패턴
- Commit 메시지 스타일
- Feature / Fix / Refactor 등 작업 유형
- 프로젝트 지속성 및 Repository 분산 정도
- 개발자 유형
- Developer DNA
- 공유용 결과 카드

### 1.2 핵심 가치

> "내 GitHub를 분석하면 내가 어떤 개발자인지 알 수 있다."

단순 통계 서비스가 아니라 **개인화된 결과를 공유하고 싶게 만드는 것**을 핵심으로 한다.

## 비동기 처리

MVP에서는 GitHub API 호출과 분석 작업을 동기 처리하지 않는다.

```text
API Server
   │
   └── AnalysisJob 생성
            │
            ▼
      Redis Job Queue
            │
            ▼
        Worker
```

분석 작업이 오래 걸려도 사용자 요청을 block하지 않도록 한다.

## Infrastructure

MVP 기준 Railway 사용을 권장한다. (AWS 대비 초기 운영 부담이 적고, Git push 기반 배포로 오픈소스 컨트리뷰터가 쉽게 따라할 수 있음)

- Railway Service (frontend / backend / worker 각각 별도 서비스로 배포)
- Railway 내장 도메인 라우팅 (ALB 역할 대체, HTTPS 자동 처리)
- Railway PostgreSQL (RDS 대체)
- Railway Redis (ElastiCache 대체 + Job Queue 겸용, SQS 대체)
- Cloudflare R2 (S3 대체, S3 호환 API + CDN 역할 겸용으로 CloudFront 대체)
- Railway 환경변수 / Shared Variables (Secrets Manager 대체)
- Railway Logs & Metrics (CloudWatch 대체, MVP 수준)

단, 로컬 개발은 Docker Compose로 전체 환경을 실행할 수 있어야 한다.

### AWS 대비 트레이드오프

- 장점: 설정 단순, 배포 속도 빠름, 비용 예측 쉬움(사용량 기반 소액 과금), 오픈소스 컨트리뷰터의 self-hosting 진입장벽 낮음.
- 단점: SQS/DLQ 같은 관리형 큐가 없어 재처리·Visibility Timeout 로직을 애플리케이션 레벨(Redis)에서 직접 구현해야 함. 트래픽이 커지면 ECS/K8s 대비 세밀한 오토스케일링·리전 다중화 옵션이 제한적 — 이 시점에는 AWS 마이그레이션을 재검토한다.

# 6. GitHub OAuth 설계

## 인증 흐름

```text
Browser
  │
  │ GitHub Login
  ▼
Backend
  │
  │ Authorization Request
  ▼
GitHub
  │
  │ Authorization Code
  ▼
Backend Callback
  │
  ▼
Access Token
  │
  ▼
User 생성/조회
  │
  ▼
Session 발급
```

### 원칙

- GitHub 비밀번호는 절대 서버에 저장하지 않는다.
- Access Token은 필요한 최소 권한만 요청한다.
- 가능하면 Public Repository 분석을 기본값으로 한다.
- Private Repository 접근은 별도 동의 및 권한 설계를 거친다.
- Token은 암호화 저장하거나 최소한 외부 노출을 방지한다.

# 10. Commit 메시지 분석

Commit message를 정규화한 뒤 작업 유형을 분류한다.

예시:

```text
feat: add oauth login
→ FEATURE

fix: resolve login bug
→ FIX

refactor: simplify user service
→ REFACTOR

docs: update README
→ DOCUMENTATION

test: add login test
→ TEST
```

초기에는 Conventional Commits + keyword 기반 규칙으로 구현한다.

예:

```text
feat / add / implement / create
→ FEATURE

fix / bug / hotfix / patch
→ FIX

refactor / cleanup / simplify
→ REFACTOR

docs / readme / documentation
→ DOCUMENTATION

test / spec
→ TEST
```

추후 ML/LLM을 사용해 분류 정확도를 개선한다.

# 21. 장애 및 재처리

분석은 비동기 Job으로 관리한다.

```text
PENDING
   ↓
COLLECTING
   ↓
ANALYZING
   ↓
COMPLETED
```

실패:

```text
FAILED
   ↓
Retry
```

GitHub API 오류:

- Exponential Backoff
- 최대 Retry 횟수
- Rate Limit 확인

Worker 장애:

- Queue 메시지 재처리 (Redis 큐에서 재획득)
- Visibility Timeout (처리 중 메시지에 TTL을 두고, 만료 시 재큐잉)
- Dead Letter Queue (재시도 횟수 초과 메시지를 별도 Redis 키/DB 테이블로 이동)

를 애플리케이션 레벨에서 직접 구현한다 (SQS의 관리형 기능을 Redis 기반으로 대체).

# 23. 성능 목표

MVP 목표:

- 로그인: 2초 이내
- 분석 Job 생성: 500ms 이내
- 일반적인 GitHub 계정 분석: 30~120초
- 결과 페이지: 2초 이내
- Badge 응답: 500ms 이내

분석 시간은 계정의 Repository/Commit 수에 따라 달라질 수 있다.

# 24. 관측성

Railway 환경에서는:

```text
Railway Logs & Metrics
 ├── API latency
 ├── GitHub API error
 ├── Queue depth
 ├── Worker failure
 ├── Analysis duration
 └── AI request/cost
```

를 모니터링한다. Railway 기본 관측성은 AWS CloudWatch 대비 지표가 단순하므로, 위 항목 중 Queue depth / Analysis duration / AI cost처럼 커스텀 지표가 필요한 부분은 애플리케이션에서 직접 로깅하거나 조기에 OpenTelemetry를 도입한다.

향후 OpenTelemetry + Prometheus/Grafana 도입을 검토한다.

# 28. 오픈소스 전략

목표는 단순히 코드를 공개하는 것이 아니다.

```text
무료 공식 서비스
       ↓
사람들이 사용
       ↓
결과 카드 공유
       ↓
새 사용자 유입
       ↓
GitHub Repository 방문
       ↓
Star / Fork
       ↓
Contributor 유입
       ↓
기능 증가
       ↓
더 많은 사용자
```

## 핵심 지표

초기에는 매출보다 다음을 본다.

- GitHub Star
- Fork
- Contributors
- 공식 서비스 분석 횟수
- 공유 카드 생성 횟수
- Badge 설치 수
- 재방문율

      ↓

라고 느끼고 **공유 버튼을 누르게 만드는 것**이 MVP의 가장 중요한 성공 기준이다.
